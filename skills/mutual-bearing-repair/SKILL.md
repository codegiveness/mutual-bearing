# Mutual Bearing Repair

Use this method to find and repair the cause of a collaboration problem. It is not an interview, a postmortem template, or a mode that persists after the repair. If the user's correction already says what to change, make that change instead of diagnosing.

## 1. Locate the earliest divergence that still matters

Recover the relevant request, decisions, reported experience, evidence, and the work actually produced. Find the earliest point where the work diverged from what the user wanted and that still affects the outcome. Keep apart what the user said and what you inferred, what was authorized and what was only proposed, and what happened and what was merely claimed. Do not attribute motives, personality, intelligence, or a medical condition to anyone.

Use the questions that can change the next action. They overlap and are not a checklist:

- **Direction:** Are you solving the intended problem? Ask about an unresolved user-owned choice; recover and use an answer that is already available. A goal that is still forming may need a concrete contrast, not a tighter specification.
- **Evidence:** Does the work rest on an unsupported fact or explanation? Accept the reported experience, investigate its cause, and name missing evidence. Agreement does not supply a missing fact.
- **Proxies and boundaries:** Is the work optimizing something easy (brevity, visible activity, pleasing the user, defending earlier work) instead of the agreed result? Correct the choice or the success check, not a presumed motive. Being able to act is not permission to act.
- **Capability:** Is access, context, a tool, a skill, or a feasible method missing? Use what is available or name the actual blocker. Rewriting a clear request does not supply a missing capability.
- **Execution and handoff:** Was the agreement understood but implemented wrongly, or did a correction fail to reach dependent work? Trace affected outputs and pending actions. For a failed handoff, check what the recipient actually received or could access, not just what the sender recorded.

Treat causes as hypotheses until evidence supports them; several can coexist. Do not blame the user or prescribe a remedy from a label alone.

## 2. Apply the smallest adequate repair

- When the disputed interpretation matters, state it and its consequence plainly. Ask about an unresolved decision in a way that leaves room to reject your framing; if context already resolves it, apply that answer.
- Repair the affected reasoning, artifacts, queued actions, or handoff, preserving unaffected decisions and permissions. An already-authorized repair needs no new approval; a new consequential commitment does. Keep independent work moving.
- If a completed action cannot be undone, state the outcome and the available remedies. Do not promise rollback or take a new consequential action without authority.

## 3. Check, then return to the task

- Check an observable result of the repair against the actual goal, not a convenient proxy. If the repair changed a rule, workflow, or control, check that authorized work still proceeds and required safeguards still hold.
- Say which state applies: repaired, incomplete, blocked on missing evidence, or waiting on a user decision.
- If repeated instructions have already failed, examine context delivery, conflicting guidance, tool design, or an external permission control before adding more prose.
- Return to the task. Explain only what the user needs to understand the change and steer what happens next; no score, rewritten prompt, or ongoing repair mode.
